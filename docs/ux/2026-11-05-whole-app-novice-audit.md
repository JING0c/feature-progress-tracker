## 严重

### U1 新增任务的回复与发起位置失联

**在哪：**027–036，稳定画面 033。

**看到什么：**点击“新增功能”的“直接拆分”后，Codex 提出两个澄清问题。回复在“功能建议”的最近讨论中；视口却回到页顶的 GitHub 参考列表，左栏仍选中“新增功能”。必须手动找到功能建议，再切换“先讨论想法/生成修改建议”才能继续。当前新增需求通过这条路线最终保存，共 8 次点击。

**因果限制：**等待拆分时曾切换并还原视口，可能影响滚动位置，因此不把回到页顶归因于完成回调。此项主要依据是回复所在模块与发起模块不同、后续实际必须跨入口继续；滚动跳转的具体触发条件需修复前单独复现。

**为什么是问题：**用户需要自行发现另一个模块中的回复、理解两个入口的关系，并判断处理模式。很容易以为没有响应、再次提交或放弃。这里没有发生数据丢失，但有明显的任务中断风险。

**建议：**输入、澄清、拆分预览和加入功能表留在同一任务面板；分析需要提问时原位显示问题，回答后原位继续。保留人工采纳边界，去掉为了继续任务而跨模块找回复的步骤。

## 中等

### U2 项目级导航与局部操作混层，项目身份会滚出视口

**在哪：**003–004、016–018、033、052–053、071。

**看到什么：**规划页“项目总览”在左上，看板的同名入口在右上。规划页滚动后项目名和全局入口消失，只剩“项目规划书”标题；侧栏把新增、视图、核对、记录、读取文件、复制和导出放在一起，有些导航只是滚到长页面里的位置。历史详情又在这条长页面内部打开。

**为什么是问题：**同名入口换位置，不同层级的动作长得一样。用户很难保持“哪个项目、哪个页面、正在编辑还是回看”的稳定定位。

**建议：**固定项目定位与回项目列表入口；项目内目的地与表内动作分层。保持主色和现有包含关系设计，无需更换视觉风格。

### U3 进入、返回、取消和完成没有一致约定

**在哪：**019–025、040、051–053、071–073。

**看到什么：**“查看功能明细”在表右上，进去后需点“功能清单”标签返回；编辑入口右上，保存同时在右上和左下，取消只在左下。建议预览使用“返回建议/放弃本次预览”；历史详情则用左上“← 返回操作记录”。保存到看板后没有就近的“查看看板”，要找页顶“返回功能看板”，尽管这是第一次进入。

**为什么是问题：**每个任务都要求重新寻找离开和完成的位置。上下都有保存本身可以减少长表滚动，并非天然缺陷；这里的问题是取消只在下方、退出约定不一致，保存后的滚动变化又使刚改的内容难确认。页签返回本身也合理，但应与入口名称及层级一致。

**建议：**统一局部任务栏：左侧返回/取消，右侧唯一主动作；保存后保留当前功能的定位。台账写入成功后原位提供“查看看板”。历史详情目前的明确返回应成为一致规则之一。

### U4 同一功能内容被过多视图和说明包围

**在哪：**018–020、040、046–048。

**看到什么：**侧栏“功能表与视图”、表格/文档切换、六个章节、“查看功能明细”同时存在。预览同时重复多处未保存和修改数量说明，功能行落到画面下半部。源码核对与台账预览直接展示 Markdown 标记、长提交编号及原文；台账还有“目标：待规划”。

**为什么是问题：**用户先学习清单、明细、功能规划与验收等近义名称，才找到实际内容。原文适合文件处理，但作为日常审阅界面阅读成本高。

**建议：**日常以一个功能表为中心，行内看验收/技术/准备；目标、范围、风险放进“规划说明”。源码核对先展示结论和待确认项，台账先展示将新增/更新的功能，原文与提交信息按需展开。减少重复状态条。

### U5 保存和完成状态分散，出现相互矛盾的提示

**在哪：**023–024、051–052、055–056。

**看到什么：**编辑时主区写“有未保存的修改”，侧栏写“已保存·历史版本已保留”。051 已显示“台账已保存到看板·10个最细功能点”，052 顶部仍强调第 1 步已保存，提示最终确认后再生成台账。搜索建议已勾选采纳并出现在看板，备注仍为“待采纳”。

**为什么是问题：**数据确实保存了，但文字让用户反复确认“到底完成没有”。最后一项来自本轮生成内容，不能据此断言所有建议都这样，但它是实际可见的矛盾。

**建议：**统一当前状态来源，区分“上次保存”“当前未保存”“看板已同步”。生成内容中的提议状态应与采纳操作衔接，避免旧状态词一直留在正式功能中。

### U6 GitHub 候选难以按功能比较，下一步被旧主按钮抢占

**在哪：**007–013。

**看到什么：**五个候选主要显示英文描述、框架和星数，三个 IBM 候选主要区别是 Vue/React/Vanilla；没有中文说明哪些能力可以借鉴。搜完后上方“查找参考并开始规划”仍醒目，下一步“确认参考并继续”在列表底部屏外。

**为什么是问题：**用户希望参考添加、打勾、保存功能，却被要求猜技术框架的意义；也容易再次搜索，错过继续。

**建议：**展示基于真实资料的中文功能匹配摘要，技术资料折叠；当前阶段突出一个下一步，重新搜索作为次要入口。

### U7 核对到看板的步骤缺少清楚的收尾

**在哪：**043–052。

**看到什么：**“核对源码并确认规划”“按规划生成台账”“保存到看板”并排、同色；核对完成后提示查看报告，转换后出现很长的原文预览，保存后仍在该页面。新手需要自己串联三个动作和最后的看板入口。

**为什么是问题：**这些阶段各有实际意义，但页面没有清楚表达当前应做哪一步、完成后得到什么。最终确认容易变成读说明、找按钮的连续过程。

**建议：**保留源码核对和明确保存，组织为一个连续任务：核对结果 → 审阅看板变更 → 确认并查看看板。只突出当前主动作，不让未到的步骤与之竞争。

### U8 窄屏首屏被导航占满，功能内容需要横向寻找

**在哪：**075、077、079（390×844）。

**看到什么：**项目总览可正常阅读。进入规划后，桌面侧栏整体排在顶部，占约 560 像素，项目名称在其下；到功能表只能同时看到采用、大功能和部分小功能，功能介绍在右侧屏外，章节也横向超出。

**为什么是问题：**用户先经过大量不常用操作才到项目内容；看功能名称时看不到说明，查验收更费力。

**建议：**窄屏导航收为项目菜单，当前任务和返回常驻；清单用树形条目加详情，或明确提供横向滚动提示。无需把文件和导出菜单完整摊在首屏。

### U9 看板长详情造成大量空白与滚动

**在哪：**053、055–056。

**看到什么：**概览卡片包含关系清楚，但展开搜索功能后，长详情仍挤在约三分之一宽度的卡片中，其余区域留下大块空白；读到技术、准备、审核字段时卡片标题和全局返回均不在视口。

**为什么是问题：**只有一个功能的说明，却拉长整个大功能容器，用户要在空白旁连续向下读，也不易回到刚才的位置。

**建议：**保留嵌套概览，详情采用容器内整行展开或独立详情面板，并提供固定标题与关闭/返回；技术与审核等次要字段分组展开。

## 轻微

### U10 文件实现信息和候选布局增加阅读负担

**在哪：**001–002、007、011、053、075。

**看到什么：**完整绝对路径、“每3秒读取Markdown”在主要页面直接显示；新建时默认可空的目录输入与项目名同级。参考卡片四列后第五张单独一行，形成大块空白。

**为什么是问题：**这些信息有价值，但当前任务通常用不到，却推远了下一步按钮。

**建议：**目录和文件机制放在高级设置/文件位置；候选采用更紧凑、便于比较的列表。

### U11 长等待的取消约定不一致

**在哪：**015、031、044。

**看到什么：**初始规划等待 103 秒时没有可见取消；新增拆分和后续源码核对有“取消本次生成”。阶段百分比、耗时和步骤已有显示，属于应保留的反馈。

**为什么是问题：**相同的长等待，用户能否改变主意的约定不同。本轮不能由 50% 推断卡死，也没有把阶段百分比当作剩余时间。

**建议：**可安全取消的步骤统一入口，明确保留输入；不可取消时说明正在完成哪一步，避免让用户猜测。

## 建议先改的顺序

1. **先修任务结果定位与状态矛盾（U1、U5）**：影响大、边界相对明确。新增任务原位问答，保存状态一致，完成后不再显示未完成步骤。
2. **统一返回与完成操作（U3、U7）**：固定任务栏，保存到看板后提供就近入口；保留预览和明确保存，不为了省点击删除用户控制。
3. **统一项目和页面层级（U2）**：先确定整体规则，再一起调整各入口，避免继续零散补按钮。
4. **减少视图重叠和原文负担（U4、U6）**：一个日常功能表，清楚的参考功能摘要。
5. **处理窄屏与看板展开（U8、U9）**，再收紧次要信息及等待打磨（U10、U11）。

## 建议的统一结构，尚未实施

| 层级 | 目的地/动作 | 位置约定 |
| --- | --- | --- |
| 项目之间 | 项目管理器、项目切换 | 固定左上“项目总览 > 当前项目” |
| 当前项目内 | 功能表、进度看板、操作记录；规划说明作为次级入口 | 同一组固定导航，位置不随页面改变 |
| 功能表内 | 新增、编辑、AI建议、同步到看板 | 表内工具栏，不混入项目导航 |
| 一个局部任务 | 输入/澄清/预览/保存 | 左侧返回或取消，右侧唯一主要完成动作 |
| 次要工具 | 导出、复制、文件位置、恢复资料 | “更多”菜单或按需展开 |

需要人来定的主要取舍：采用少量独立页面，还是保留一个长工作区。根据本次证据，建议采用前者；也可保留长页面，但必须有稳定定位、明确任务面板和一致返回行为。本轮没有擅自改布局或交互。

## 复验方法与边界

改后使用同样需求、同一参考、同一屏幕尺寸，从空项目管理器重走上述路线。再次记录每次点击和图，不以单元测试通过代替验收。主要比较：新增结果是否原位可见；离开每个局部任务是否找到同一位置的返回；保存状态是否一致；保存后是否一眼找到看板；同一内容需经过多少层视图。

未覆盖：导入已有项目、项目数量很大时的管理、真实移动设备触控、键盘全流程/读屏器、断网恢复、Excel 导出及原生 Excel、两个项目同时生成、高并发或浏览器后退保护。本轮没有修改后复走，因为没有修改产品代码。真实 Codex 使用了当前本机登录，不是全新账号；隔离的是项目文件与该端口的浏览器业务状态。

本轮不存在足够证据认定功能保存失败或项目串写。原生弹窗工具的短暂定位/截图限制、视口切换不稳定帧也未列为产品缺陷。

## 后续用户补证：U12 草稿来源不明（中等，未修复）

用户随后提供“找回未保存的修改”窗口截图：三份内容仅标“草稿1/2/3”，均为“暂存时间未记录”，显示6585/6618/5301字符及正文节选。用户明确反馈“不理解草稿哪里来的”。这是后续补证，不计入上文78张实测截图或原11组问题。

**体验事实：**名称、字符数和相近正文无法解释来源，也无法判断哪份仍需处理。用户被迫辨认系统留下的临时状态。

**代码核实（与截图观察分开）：**`planning.html` 的 `retainDraft()` 在采用勾选、建议预览、生成规划及表格保存前等路径暂存文档；初始化将当前暂存和旧缓存合并进恢复列表，按正文去重并排除与已保存文件完全相同的内容。保存成功清理当前暂存，未清理恢复列表。记录只有正文、基准版本、生成标记及可能存在的时间，没有具体来源动作。编辑器输入暂存是另一份缓存，不能将弹窗中的三项一概归为三次手动编辑。

因此可以确定它们属于浏览器保留的规划副本，但不能确定截图中每份来自哪次操作；缺少时间也不足以判定具体产生日期。不能声称三份都还有未完成工作，更不能静默删除。

**建议：**将用户概念收敛为“有一项未保存的修改，继续编辑/查看差异”；需要恢复多项时，以真实来源动作、时间和功能差异命名。无法追溯的旧数据明确标为“早期浏览器备份，来源未记录”，提供与当前功能表比较后再决定的路径。保存成功后正确处理已消费的恢复项，避免长期显示成待办。未经数据核对不自动清理。
